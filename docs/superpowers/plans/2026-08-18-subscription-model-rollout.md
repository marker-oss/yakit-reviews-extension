## Этап 1 — фундамент мультитенанта (1.5–2 недели)

### 1.1 Таблица tenants

`internal/store/tenant_models.go` (новый):
```go
type Tenant struct {
    ID           uint      `gorm:"primaryKey"`
    Slug         string    `gorm:"size:64;not null;uniqueIndex"`
    PublicKey    string    `gorm:"size:64;not null;uniqueIndex"` // 32 байта hex из crypto/rand
    ShopOrigin   string    `gorm:"size:255;not null"`            // замена REVIEWS_SHOP_ORIGIN
    Plan         string    `gorm:"size:16;not null;default:'trial'"` // trial|free|base|pro
    Status       string    `gorm:"size:16;not null;default:'trial'"` // trial|active|grace|paused
    TrialEndsAt  time.Time
    QuotaViews   int       `gorm:"not null;default:5000"`
    CreatedAt    time.Time
}
```

### 1.2 Вырезание DefaultTenantID

- `internal/store/`: все методы, использующие `DefaultTenantID`
  (`marketplace_credentials.go:30,41`, `curation.go:224,232,279`, и т.д. —
  всего ~55-70 мест), переходят на `TenantIDFromCtx(ctx)`.
- Новый `internal/store/ctx.go`: `WithTenant(ctx, id)`,
  `TenantIDFromCtx(ctx)` (паника при отсутствии — программная ошибка).
- `SyncState` получает `tenant_id` (сейчас нет — проверить при миграции).
- `export_dirty.go`: `export_dirty_at` глобальный -> per-tenant.

### 1.3 Миграции

- Автомиграция GORM остаётся для v1 (одна строка `AutoMigrate(&Tenant{})`
  добавляется в существующий список 12 таблиц в `store.go`).
- Data-миграция: существующая установка получает `Tenant{ID:1,
  PublicKey:<сгенерирован>, Slug:"default", ShopOrigin: REVIEWS_SHOP_ORIGIN}`.
  `DefaultTenantID` удаляется после этого полностью — никаких алиасов.
- Backward-compat open-source: без `public_key` в запросе -> тенант 1
  (флаг `REVIEWS_COMPAT_SINGLE_TENANT=true` по умолчанию в одиночном
  режиме; SaaS-инстанс стартует с `false`).

### 1.4 Публичный контракт по public_key

- `GET /api/reviews?public_key=...` и `GET /api/showcase?public_key=...`:
  middleware `publicKeyAuth` кладёт `Tenant` в контекст.
- `loader.js`: `REVIEWS_EMBED_CONFIG` получает `publicKey`; все URL
  (`showcaseUrl`, `reviewsUrl`, `bundleUrl`) добавляют параметр.
  `Embed.tsx` генерирует сниппет уже с ключом.
- Статические бандлы `by-article/*.json`: путь
  `/export/{public_key}/by-article/...` — `internal/export` и
  `cmd/reviews/main.go:497` уже собирают бандлы, меняется корень пути.

### 1.5 Тесты изоляции

- `store/tenant_isolation_test.go`: два тенанта; запросы тенанта А не видят
  reviews/credentials/widget_config/showcase_rule тенанта Б (все 12 таблиц).
- `server/cors_test.go` расширить: запрос с Origin тенанта А к public_key
  тенанта Б -> 403.

Приёмка: `go test ./...` зелёный; два тенанта на одном инстансе полностью
изолированы; одиночный open-source режим работает без изменений конфига.

## Этап 2 — периметр безопасности (3–4 дня)

### 2.1 Шифрование API-ключей маркетплейсов

Сейчас `MarketplaceCredential.Payload type:text` — plaintext
(`marketplace_credentials.go:17`). В SaaS это токены чужих магазинов.

- `internal/crypto/aesgcm.go` (новый): AES-256-GCM, ключ из
  `REVIEWS_CREDENTIALS_KEY` (32 байта, base64).
- `SaveMarketplaceCredential` шифрует, `PayloadMap` расшифровывает.
- Поле-маркер `PayloadEncVersion` (`enc:v1:`), миграция существующих строк
  при старте.
- Ключ бэкапится вместе с БД отдельной инструкцией в `deploy/README.md` —
  потеря ключа = потеря всех токенов.

### 2.2 Rate limiting по тарифу

- `internal/server/ratelimit.go`: `x/time/rate` лимитер per-public_key
  (in-memory map, TTL очистки). Лимиты из `tenants.plan`:
  trial 1 rps/1000 показов день, base 5 rps, pro 10 rps.
- Счётчик показов виджета: инкремент по `public_key` при
  `/api/reviews`/`/api/showcase`; превышение `QuotaViews` -> 402 + флаг в
  админке. Хранение счётчика: таблица `usage_daily(tenant_id, date, views)`,
  сброс джобом.

### 2.3 CORS per-tenant

- `middleware.go`: `cors()` берёт разрешённый Origin из
  `tenants.shop_origin` по public_key запроса вместо глобального
  `REVIEWS_SHOP_ORIGIN` (`config.go:58`). Глобальная настройка остаётся
  только в compat-режиме.

Приёмка: дамп БД не содержит plaintext-токенов; 429 при превышении rps;
402 при превышении квоты; CORS-запрос чужого домена отклонён.

## Этап 3 — инфраструктура SaaS (2–3 дня, вариант A)

### 3.1 Скрипт создания тенанта

`deploy/create-tenant.sh` (новый, рядом с `server-deploy.sh`):
- аргументы: slug, домен магазина, тариф;
- создаёт `/srv/tenants/{slug}/.env` (порт, volume, `REVIEWS_SHOP_ORIGIN`,
  `REVIEWS_DB_DSN` sqlite `./data/{slug}/reviews.db`);
- `docker compose --profile tenant-{slug} up -d` — один сервис на тенанта,
  образ из GHCR (pipeline `release.yml:75` уже есть);
- вывод: сгенерированный public_key + готовый embed-сниппет.

Оценка ресурсов: ~40-60 МБ RAM на контейнер -> 30-40 тенантов на 4 ГБ VPS.

### 3.2 Домены и TLS

- Wildcard `*.app.{saas-domain}`; Caddy (`deploy/Caddyfile`) с DNS-01
  через API регистратора или on-demand TLS по списку тенантов.
- Каждый контейнер за своим поддоменом `{slug}.app.{saas-domain}`;
  админка и виджет на одном порте как сейчас.

### 3.3 Бэкапы

- cron: `sqlite3 .backup` каждого `/srv/tenants/{slug}/data` в
  `/srv/backups/` + еженедельная выгрузка в S3-совместимое хранилище
  (SelCloud/Yandex Object Storage, ~100 руб/мес).

Приёмка: новый тенант поднимается за <=10 минут скриптом; рестарт VPS не
теряет данные; бэкап восстанавливается на чистую машину.

## Риски

- Яндекс Кит сам встроит отзывы — окно открыто пока платформа в бете;
  страховка: партнёрка (Этап 6) и фокус на агрегации WB/Ozon, а не только Кит.
- Churn 7-12%/мес у мелких селлеров -> юнит-экономика сходится только при
  сетке тарифов; единственный тариф 300 руб не покрывает инфраструктуру.
- Один VPS = единая точка отказа: виджет отказоустойчив только после переезда
  на вариант B с CDN (Этап 7). На этапе 30 тенантов принимаем риск,
  бэкапы ежедневные.
