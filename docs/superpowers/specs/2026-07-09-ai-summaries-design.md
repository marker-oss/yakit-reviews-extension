# ИИ-сводки отзывов (саммаризация) — дизайн v1

Дата: 2026-07-09. Статус: утверждён к планированию.

## 1. Контекст и стратегическая рамка

Продвижение виджета среди продавцов Яндекс Кита упёрлось в ограничения платформы
(доставка только через Тег-менеджер Метрики, санитайзер режет скрипты). Решение
сессии — репозиционирование: продукт развивается как **платформа работы с
отзывами маркетплейсов** (сбор → показ → аналитика → ответы), а не «виджет для
Кита».

Зафиксированные решения:

- **Модель**: open-core по образцу Chatwoot/Postiz. Self-hosted версия — полное
  ядро, ИИ-фичи требуют самостоятельной установки AI-сервиса и своего
  LLM-ключа. SaaS-версия (позже) — hosted, ключи и настройка на нашей стороне.
- **Платящая аудитория**: агентства/интеграторы (мультиклиентские установки,
  отчёты) и ИИ/агентный сегмент (доступ агентов к данным отзывов).
- **Порядок ИИ-фич**: саммаризация → ИИ-ответы на отзывы → интеграция с
  агентами поддержки (MCP/события).
- **Бренд**: сначала фичи в текущем репо; новый брендированный репо/форк
  (с Postgres) — после проверки спроса. Имя и структура репо не меняются.
- **Первая фича**: саммаризация, видимая и в админке, и в виджете, с
  обязательным ручным утверждением перед публикацией.

## 2. Архитектурный принцип

Ядро становится **хранилищем модерируемых ИИ-артефактов** с тремя поверхностями
интеграции. ИИ-логика вынесена в отдельные воркеры; ядро без них полностью
работоспособно.

```
ядро (истина + артефакты + модерация + доставка)
  ├── Worker API:  GET задачи/данные → POST артефакт-драфт      ← AI-воркеры
  ├── События:     webhooks «новый отзыв», «негатив»            → фаза 2+
  └── MCP-фасад:   read/act для внешних агентов                 → фаза 2+
```

Каждая будущая ИИ-фича = новый тип артефакта + воркер над тем же контрактом.
Ядро меняется минимально (тип артефакта, модерация, доставка).

Выбор «микросервис, а не встроенный LLM-клиент» осознанный: (а) трение
self-hosted установки — клин конверсии в SaaS; (б) в SaaS один центральный
AI-сервис с нашими ключами обслуживает много клиентских ядер; (в) контракт
позволяет подключить произвольного агента вместо референсного воркера;
(г) сервис переживёт будущий форк ядра на Postgres.

Референсный воркер: **Go**, в этом репо (`cmd/ai-service`), опциональный сервис
в docker-compose (profile `ai`). SaaS-оркестратор — будущий закрытый репо на
базе референса; здесь не проектируется.

## 3. Скоуп v1

Входит: сервисные токены; Worker API (3 эндпоинта); таблица `ai_artifacts`;
вычисление задач саммаризации; референс-воркер; страница «ИИ-сводки» в админке;
блок сводки в виджете через существующий статический экспорт.

Не входит (следующие фазы): события/вебхуки; MCP-фасад; ИИ-ответы; дашборд
аспектов/сентимента (aspects копятся в payload уже в v1, но не
визуализируются); map-reduce для сверхбольших артикулов; биллинг/SaaS.

## 4. Контракт Worker API

Аутентификация: `Authorization: Bearer <token>`. Сервисные токены создаются в
админке (Настройки → Интеграции), хранится только хэш, скоуп `worker`.
Токен можно отозвать. Все эндпоинты отвечают 401 без валидного токена.

### GET `/api/worker/tasks?type=summary`

Ядро вычисляет, каким артикулам нужна сводка:

- видимых отзывов ≥ порога (настройка `summary_min_reviews`, дефолт 5), и
- нет approved-сводки (`reason: "missing"`), или её `source_hash` ≠ текущему
  (`reason: "stale"`), или запрошена принудительная регенерация
  (`reason: "forced"`);
- и нет свежего драфта с текущим `(source_hash, prompt_version)` в статусе
  `draft`/`rejected` (защита от повторной генерации отклонённого).

Ответ: `{"tasks": [{"article", "productTitle", "reviewCount", "sourceHash",
"reason"}]}`, отсортировано: forced → missing → stale; лимит 200 задач.

### GET `/api/worker/articles/{article}/reviews`

Ответ: `{"article", "productTitle", "sourceHash", "reviews": [{"rating",
"text", "publishedAt"}]}` — только видимые отзывы, без ПД (имена и медиа не
передаются: для сводки не нужны). `sourceHash` — SHA-256 отсортированного
списка ID видимых отзывов; считается ядром единообразно с `tasks`.

### POST `/api/worker/artifacts`

Тело: `{"type": "summary", "article", "sourceHash", "promptVersion", "model",
"payload"}`. Валидация payload по схеме типа (см. §6). Идемпотентность:
уникальный ключ `(type, article, source_hash, prompt_version)`; повторный POST
апсертит существующую строку, если она не `approved`/`superseded`: обновляет
payload/model и переводит `rejected` обратно в `draft` (достижимо только через
forced-регенерацию — обычные задачи rejected-состав не выдают). Ответ 201/200
с артефактом; 409 не используется. Успешный POST снимает forced-флаг артикула.

Гонки: если состав отзывов изменился, пока воркер работал, драфт сохранится со
старым `sourceHash`, а артикул снова появится в `tasks` — система сходится сама.

## 5. Модель данных

Таблица `ai_artifacts`:

| колонка | тип | примечание |
|---|---|---|
| id | integer pk | |
| type | text | v1: `summary` |
| article | text | индекс |
| payload | text (JSON) | схема по типу |
| model | text | из воркера |
| prompt_version | text | из воркера |
| source_hash | text | |
| status | text | `draft` / `approved` / `rejected` / `superseded` |
| created_at / updated_at / approved_at | timestamp | |

Уникальный индекс: `(type, article, source_hash, prompt_version)`.

Форсированная регенерация: маленькая таблица `ai_regen_requests (type, article,
requested_at)` — кнопка «Перегенерировать» пишет строку, задача получает
`reason: "forced"`, успешный POST драфта строку удаляет.

Статусная модель:

- `draft` — создан воркером, ждёт модерации; правки в админке пишутся в payload
  драфта.
- `approved` — публикуется в экспорт. При апруве нового артефакта предыдущий
  `approved` того же `(type, article)` переводится в `superseded` в одной
  транзакции. Инвариант: не более одного `approved` на `(type, article)`.
- `rejected` — скрыт; тот же состав отзывов повторно не генерится (уникальный
  ключ), новый состав/промпт — снова придёт драфтом.
- «Устарела» (stale) — **вычисляемый признак**, не статус: `source_hash`
  approved-строки ≠ текущему хэшу. Approved продолжает публиковаться до апрува
  замены; виджет не видит ничего, кроме `approved`.

## 6. Payload сводки (схема)

```json
{
  "overall": "1-2 предложения общего впечатления",
  "pros": ["строка", "..."],
  "cons": ["строка", "..."],
  "aspects": {
    "качество": {"sentiment": 0.9, "mentions": 47}
  }
}
```

Ограничения (валидируются ядром при POST и админкой при правке): `overall` ≤
400 символов; `pros`/`cons` — до 6 пунктов по ≤ 80 символов; `aspects` — до 10
ключей, `sentiment` ∈ [0,1], `mentions` ≥ 1. `aspects` в v1 не отображаются в
виджете — копятся как сырьё для дашборда сентимента (фаза 2+).

## 7. Референс-воркер `cmd/ai-service`

Отдельный бинарник. Конфиг через env: `CORE_URL`, `WORKER_TOKEN`,
`LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`, `POLL_INTERVAL` (дефолт 15m),
`RUN_LIMIT` (артикулов за прогон, дефолт 50), `LLM_INPUT_BUDGET` (токены,
дефолт 24000).

Цикл: `tasks` → для каждой: отзывы → промпт → LLM → валидация → POST драфта.

- **LLM-клиент**: OpenAI-совместимый chat completions, JSON-режим
  (`response_format: json_object`). Совместим с OpenAI, OpenRouter, DeepSeek,
  YandexGPT (совместимый эндпоинт), Ollama/vLLM.
- **Промпт**: шаблон зашит в бинарник; `promptVersion` — константа рядом с
  шаблоном, меняется при каждом изменении текста промпта. Системная часть:
  роль аналитика отзывов, русский язык, запрет выдумывать факты и упоминать
  имена, требование схемы §6. Пользовательская часть: название товара + список
  отзывов «оценка/дата/текст».
- **Отбор при переполнении бюджета**: весь негатив (≤3★) новее двух лет, затем
  остальные отзывы от новых к старым, до `LLM_INPUT_BUDGET` (оценка: 1 токен ≈
  3 символа русского текста). Эвристика фиксируется в коде комментарием.
- **Невалидный ответ модели**: один ретрай с добавленным описанием ошибки
  валидации; повторный мусор — скип артикула, лог.
- **Ошибки LLM/сети**: экспоненциальный бэкофф; после 3 неудач подряд по
  артикулу — скип до следующего прогона. Воркер стейтлесс: состояние ошибок
  живёт в памяти прогона.

docker-compose: сервис `ai-service` под `profiles: [ai]`, чтобы обычная
установка его не поднимала.

## 8. Админка

Новая страница «ИИ-сводки» (место в навигации — по плану консолидации навигации
из роадмапа):

- Список артикулов со сводками: колонки — товар, статус (approved / драфт
  ожидает / устарела / отклонена), возраст сводки, число отзывов в основе.
- Карточка сводки: текущая approved (если есть) и ожидающий драфт рядом;
  редактирование полей драфта (overall — textarea, pros/cons — редактируемые
  списки); кнопки **Утвердить** / **Отклонить** / **Перегенерировать** (ставит
  флаг forced для задачи).
- Настройки (на существующей странице настроек): порог `summary_min_reviews`,
  тумблер «Показывать сводки в виджете» (влияет на экспорт).
- Пустое состояние: если сервисных токенов нет — подсказка «подключите
  AI-сервис» со ссылкой на документацию и генерацией токена.

Существующая страница «Встраивание»/настройки получают раздел «Интеграции»:
создание/отзыв сервисных токенов (показ значения один раз при создании).

## 9. Виджет и экспорт

Экспорт добавляет поле `summary` в существующие `reviews-data/by-article/{article}.json`
— только `approved` и только при включённом тумблере. Поле: `{overall, pros,
cons, reviewCount, generatedAt}` (aspects не экспортируются). Ни одного нового
HTTP-запроса на клиенте; отсутствие поля = блока нет (бесшовная деградация,
старые экспорты валидны).

Виджет: блок «Покупатели отмечают» над лентой отзывов — overall, чипы
плюсов/минусов, подпись «Сводка сгенерирована ИИ на основе N отзывов».
Стилизация в существующей теме виджета; Shadow DOM как сейчас.

## 10. Ошибки, лимиты, стоимость

- Воркер недоступен → ядро живёт, сводки стареют; возраст виден в админке.
- `RUN_LIMIT` (50) защищает от неожиданного счёта при первом прогоне большого
  каталога; полный каталог догоняется за несколько прогонов.
- Ожидаемая стоимость: модель класса gpt-4o-mini/DeepSeek, ~10–20k входных
  токенов на артикул → доли цента за сводку; каталог 1000 артикулов — единицы
  долларов, инкрементальные обновления — копейки.

## 11. Тестирование

Ядро (Go, существующий тест-харнесс):
- вычисление задач: пороги, missing/stale/forced, исключение rejected-состава;
- Worker API: 401 без токена, идемпотентный POST (двойной POST → один драфт),
  валидация payload;
- статусные переходы: апрув переводит предыдущий approved в superseded
  (транзакция), инвариант одного approved;
- экспорт: только approved, уважает тумблер, старые JSON без поля валидны.

Воркер:
- сборка промпта (детерминированный снапшот-тест);
- отбор отзывов под бюджет (негатив приоритетнее, порядок по дате);
- LLM-клиент против httptest-мока: успех, невалидный JSON → ретрай → скип,
  5xx → бэкофф;
- e2e: фейковый LLM + ядро в тест-режиме → драфт появился в БД.

Ручная приёмка: прогон на данных shegida дешёвой моделью, оценка качества
русского текста глазами, апрув 2–3 сводок, проверка блока в виджете на
демо-странице.

## 12. Следующие фазы (для ориентира, не в скоупе)

1. **ИИ-ответы**: тип артефакта `reply` (per review), та же модерация,
   публикация через MP reply publishing из существующего роадмапа.
2. **События**: вебхуки «новый отзыв ≤2★», «новый вопрос» → n8n/TG/саппорт.
3. **MCP-фасад**: read (отзывы, сводки, статистика) + act (драфт ответа) поверх
   тех же токенов со скоупами.
4. **Дашборд аспектов**: визуализация накопленных `aspects` (тренды, алерты).
5. **SaaS**: закрытый оркестратор воркеров (мульти-инстанс, очередь, биллинг),
   брендированный форк ядра на Postgres.
