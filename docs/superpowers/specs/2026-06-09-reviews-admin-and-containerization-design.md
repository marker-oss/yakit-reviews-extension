# Reviews: контейнеризация и админка — общая спецификация

Дата: 2026-06-09
Статус: дизайн согласован, разбит на этапы
Ветка отсчёта: `feat/yandex-market-adapter` (новые этапы — отдельные ветки)

## Контекст и цель

Сервис `reviews` (Go) собирает отзывы с маркетплейсов (WB, Yandex Market;
Ozon — стаб) в SQLite/Postgres и отдаёт их встраиваемому виджету
(`web/reviews-widget`, ванильный JS, Shadow DOM). Сейчас система строго
одно-арендная, без аутентификации, API только на чтение, конфигурация —
через env и файл маппинга `data/shegida-product-links.json`.

Две цели:

1. **Контейнеризация** — самодостаточный Docker-образ и простая настройка
   для сторонних пользователей (self-hosted).
2. **Админка** — веб-панель с визуальным редактором виджета и управлением
   выдачей/агрегацией отзывов для главной страницы и карточек товара.

## Ключевые решения (зафиксированы)

| Решение | Выбор |
|---|---|
| Модель развёртывания | Self-hosted single-tenant **сейчас**, схема и API проектируются под SaaS-мультиарендность **позже** |
| Авторизация | Логин/пароль (argon2id) + серверная сессия в БД, httpOnly+Secure cookie |
| Фронтенд админки | SPA с билдом (Vite), вшит в Go-бинарник через `go:embed` |
| Контролы редактора | Цвета/тема, макет/раскладка, видимость элементов, типографика/отступы |
| Агрегация витрины | Авто-правила + ручной pin/скрытие |

## Архитектура

Один Go-бинарник (`reviews serve`) отдаёт четыре поверхности:

| Поверхность | Путь | Доступ |
|---|---|---|
| Публичное чтение (виджет) | `GET /api/reviews`, `GET /api/widget-config` | открыто (+ CORS-allowlist, rate-limit) |
| Admin API | `/admin/api/*` | сессия обязательна |
| Admin SPA | `/admin/*` | сессия (редирект на логин) |
| Setup-визард | `/setup` | доступен только пока нет ни одного админа |

SPA админки и файлы виджета вшиваются в бинарник через `go:embed`: в рантайме
нет Node, образ — один статический бинарник.

### Доставка конфига в виджет

`loader.js` запрашивает `GET /api/widget-config?context=product|homepage` → JSON
(тема, макет, видимость) и применяет его, мёржа с `window.REVIEWS_EMBED_CONFIG`.
Визуальный редактор в live-preview встраивает **тот же** виджет, указывая на
черновик конфига; действие «Опубликовать» делает черновик активным.

## Модель данных (с заделом под SaaS)

- Во все арендо-зависимые таблицы (`reviews`, `products`,
  `product_marketplace_links`, конфиги) добавляется `tenant_id` со значением по
  умолчанию для единственного арендатора сейчас — включение SaaS позже не ломает
  схему.
- Новые таблицы:
  - `admin_users` — id, tenant_id, login, password_hash (argon2id), created_at.
  - `sessions` — token (непредсказуемый), user_id, expires_at, created_at.
  - `widget_configs` — tenant_id, context (`product`|`homepage`), version, payload (JSON),
    is_active, created_at. Версионируется → возможен откат.
  - `showcase_rules` — tenant_id, авто-правила витрины (JSON или поля).
- Курация: в `reviews` добавляются `visibility` (`visible`|`hidden`) и `pinned`
  (bool) — ручное управление поверх авто-правил.
- Маппинг артикул→ссылка переносится из `data/shegida-product-links.json` в БД
  (таблица или поле конфига), редактируется из UI.

## Безопасность

- Пароль — argon2id, в `admin_users.password_hash`.
- Сессия — запись в `sessions`, клиенту непредсказуемый токен в cookie
  `httpOnly + Secure + SameSite=Lax`, с истечением и продлением.
- CSRF-токен (double-submit cookie) на все изменяющие запросы.
- Rate-limit на логин, generic-ответ при неверных кредах.
- Security-заголовки: CSP, X-Frame-Options, X-Content-Type-Options и т.п.
- Секреты маркетплейсов **никогда** не возвращаются в API — поля только на
  запись, наружу отдаётся лишь статус «задан/не задан».
- Публичное чтение остаётся открытым (виджет на чужих сайтах), но с
  CORS-allowlist доменов и rate-limit.

## Функциональные требования к админке

- **FR-1. Аутентификация.** Setup-визард при первом запуске (создание админа,
  доступен только пока нет пользователей) → логин/выход → смена пароля.
- **FR-2. Дашборд.** Всего отзывов, средняя оценка, разбивка по маркетплейсам,
  статус и время последнего sync, ошибки последних `sync_runs`.
- **FR-3. Подключения маркетплейсов.** Вкл/выкл WB/YM/Ozon; ввод/обновление
  токенов (write-only); «проверить подключение»; ручной запуск sync; история
  `sync_runs`.
- **FR-4. Управление отзывами.** Список с фильтрами (маркетплейс, оценка,
  наличие фото, артикул, текстовый поиск) и пагинацией; действия —
  скрыть/показать, закрепить, просмотр ответа продавца и медиа.
- **FR-5. Витрина (агрегация).**
  - *Главная:* авто-правила (оценка ≥ N, есть фото, мин. длина текста, свежесть,
    сортировка) формируют пул + ручной pin/скрытие конкретных отзывов;
    предпросмотр результирующей выборки.
  - *Карточка товара:* настройки выдачи по артикулу (сколько, сортировка,
    фильтр по оценке).
- **FR-6. Визуальный редактор** (live-preview настоящего виджета):
  - Цвета/тема (CSS-переменные, светлая/тёмная).
  - Типографика и отступы (шрифт — наследовать от сайта или свой, размеры,
    скругления, плотность).
  - Макет (список/сетка/карусель, число колонок, кол-во на странице,
    «показать ещё»/пагинация).
  - Видимость элементов (фото, ответы продавца, плюсы/минусы, бейджи
    маркетплейсов, распределение оценок, фильтры).
  - Черновик → «Опубликовать» (версионируется, откат возможен).
- **FR-7. Встраивание.** Генерация сниппета (`<script>` + `window.REVIEWS_EMBED_CONFIG`)
  с указанием контекста (главная/карточка), копирование, инструкция по установке.
- **FR-8. Настройки.** Шаблон URL товара, маппинг артикул→ссылка, интервал sync.

## Контейнеризация

- **Dockerfile** (multi-stage): stage builder (golang + node собирает SPA и
  бинарник) → stage final (distroless/static или scratch, только бинарник
  ~10–15 МБ).
- **docker-compose.yml**: сервис `reviews` + named volume для SQLite
  (`REVIEWS_DB_DSN=/data/reviews.db`); опциональный профиль Postgres.
- **`.env.example`** со всеми ключами конфигурации и комментариями;
  `docker-compose up -d` поднимает всё; setup-визард создаёт админа при первом
  входе.
- **Sync в контейнере**: встроенный планировщик в процессе `serve`
  (использует существующий `REVIEWS_SYNC_INTERVAL`) — systemd-timer не нужен;
  ручной триггер sync — из админки.
- **Персистентность**: SQLite-файл обязательно в named volume.
- **Секреты**: пока через env; позже — зашифрованно в БД через админку.

## Дорожная карта (этапы)

Каждый этап — отдельная ветка, спека и план реализации.

1. **Контейнеризация.** Dockerfile, docker-compose, volume,
   встроенный планировщик sync в `serve`, `.env.example`. Ничего не блокирует.
2. **Auth + каркас админки + write-API.** Таблицы `admin_users`/`sessions`,
   setup-визард, login/logout, auth-middleware, CSRF, security-заголовки,
   `tenant_id` в схеме, каркас SPA (`go:embed`), базовые write-эндпоинты.
3. **Управление и курация отзывов.** Список/фильтры/модерация (FR-4), флаги
   `visibility`/`pinned`, авто-правила витрины (FR-5), дашборд (FR-2),
   подключения маркетплейсов (FR-3).
4. **Визуальный редактор.** Live-preview, тема/макет/типографика/видимость
   (FR-6), `widget_configs` с версионированием, доставка конфига в виджет
   (`/api/widget-config`), генерация сниппета (FR-7).

## Открытые вопросы

- Конкретный фреймворк SPA (Svelte / Preact / React) — решается на этапе 2.
- Стратегия шифрования секретов в БД (этап перехода с env) — отдельно, не в
  рамках текущих этапов.
- Детали мультиарендной активации (регистрация, биллинг) — вне объёма, схема
  лишь подготовлена.
